**Fase 2: Plan**

Tjenesten får Next.js som eneste konsument og Wonderwall foran BFF/backend. Innbyggerens ID-porten-sesjon brukes til å hente et ID-porten-token. Backend leser kun `pid` fra et verifisert token, veksler det via TokenX til PDL og returnerer navn til frontend.

| Område | Plan |
|---|---|
| Arkitektur | Ktor REST-endepunkt, uten database |
| Autentisering | Wonderwall + ID-porten til `pid`; ingen Azure eller saksbehandler-roller |
| PDL-kall | TokenX for service-to-service-kall mot PDL |
| Feil | PDL-feil gir `503`; logg metadata uten fnr eller navn |
| Observabilitet | Prometheus-tellere for oppslag/minutt og feilandel, samt health-endepunkter |
| Nais | `idporten.enabled`, `tokenx.enabled`, `wonderwall.enabled`, eksplisitt `accessPolicy.inbound/outbound` |
| Test | Ktor `testApplication`, test for gyldig token, manglende token, PDL 503 og data som ikke logges |

Personopplysninger og autentisering er rød sone: `pid`-håndtering, tokenvalidering, TokenX og PDL-kall må gjennomgås grundig. Rød-sone-koden implementeres ikke før du eksplisitt ber om det.

I denne kodebasen finnes ingen Next.js-frontend, så frontendens eksakte adresse må antas og legges inn som eksplisitt inbound-policy.
